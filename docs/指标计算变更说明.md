## 二、各次改动

### 1. 接入指标引擎（`f2f70e8`）

**引擎**
- 放在 `backend/vendor/opinion_metric_engine`，版本 engin_cli 1.9.2（上游提交 `3969468`）。
- 没有带上游的 `settings_local.py`（里面是线上库和推送凭据）；运行时配置全部由 smc 传入。
- 新增依赖 `pandas>=2.2`、`numpy>=1.26`。上游要求 pandas ≥ 3，但 Docker 镜像是 Python 3.10 装不了；引擎自带测试在 pandas 2.3 和 3.1 上结果一致，所以放宽到 2.2。

**逻辑独立**
- 每次计算在独立子进程里跑，主服务不加载 pandas；算挂了、内存冲高都不影响采集。
- 自己的定时、自己的运行记录表 `src_opinion_metric_run`；服务重启时把没跑完的记录标成「中断」。

**页面**
- 系统设置新增「指标计算」开关，打开后左侧菜单出现「指标计算」页。
- 指标计算页五个分页：计算（立即计算、运行记录）、景区与参数、定时、推送、推送表。
- 「建表」按引擎自带的建表语句创建六张 ADS 表，已有的不动。

**六张产出表**

| 简称 | 表 |
|---|---|
| 核心指标 | `ads_trf_social_opinion_comment_core_di` |
| 平台分布 | `ads_trf_social_opinion_comment_platform_di` |
| 维度得分 | `ads_trf_social_opinion_comment_dimension_score_di` |
| 关键词云 | `ads_trf_social_opinion_comment_content_di` |
| 下钻明细 | `ads_trf_social_opinion_drill_analysis_di` |
| 大盘 KPI | `ads_trf_social_opinion_macro_gran_metric_di` |

### 2. 推送对齐下游网关 + 报文预览 + 计算配置（`caeea87`）

**推送**
- 鉴权默认改成 `xpftkey: pfk_…`，不带 `Bearer` 前缀（下游 quickBiData 网关的方式）。Bearer 方式仍可配：请求头填 `Authorization`、前缀填 `Bearer `。
- 各表默认主键（pkId）对齐网关，下钻表与客户给的报文样例一致：
  `scenic_id, emotion_word, emotion_type, channel, work_id, comment_id, publish_time, travel_date`。
  其余几张取上游线上配置。页面上每张表仍可改。
- 新增「预览报文」：按已保存的配置组一个真实请求（curl 格式，令牌打码，数据取表里最新一行），不发送，用来对照下游接口样例。
- 鉴权三个输入框加了标签，下方实时显示实际发出的请求头。

**景区与参数**
- 「计算的景区」和「计算参数」合成一张「计算配置」：范围 → 取数 → 口径 → 产出 → 存储。
- 每一项下面一行说明 + 影响哪几张表；细节收进 ⓘ，一条一行。
- 鼠标移到某一项，右侧 ADS 表高亮它影响的表；关掉下钻 / 大盘时右侧对应表标「不产出」。

**各参数影响的表**（对照引擎代码确认）

| 参数 | 影响 |
|---|---|
| 景区、取数回溯、往前重跑、缺数回补、写入 ADS 表、ADS 库 | 全部 6 张表 |
| 得分权重 | 核心指标、维度得分、大盘 KPI |
| 关键词保留 | 关键词云 |
| 下钻明细（及其过滤、掩码） | 下钻明细 |
| 大盘 KPI 开关 | 大盘 KPI |

> ⚠️ 已经保存过推送配置的环境会保留旧的 `Authorization` / `Bearer `，部署后到「推送」页把请求头改成 `xpftkey`、前缀清空再保存。

### 3. 按景区配置推送哪几张表（`e2b57b3`）

- 「推送表」页顶部新增「按景区推送」勾选表（景区 × 6 张表）。
- 第一行「默认」= 每张表的「默认推送」开关；没单独添加的景区按它推。
- 单独添加的景区只推它那一行勾选的表；一张都不勾 = 不推送；「恢复默认」删除单独配置。
- 只管推不推；表名、主键、字段仍按每张表的设置。计算和写库不受影响，6 张表照常全写。

### 4. 下钻表关键字过滤（`ff19719`）

开启「只收评论内容含关键字的」时：

- **只看评论自己的内容**，不看帖子 / 笔记 / 作品标题。
- **关键字 = 本景区启用的主关键字 + 附关键字。**
- **修了一个 bug**：引擎自带的查法把 `src_opinion_scenic_filter_word` 整张表都当成采集关键字，不分附关键字和过滤关键字，也不看是否停用——含「代运营」「很差」这类过滤关键字的评论反而会被收进下钻表。现在由 smc 自己查词再交给引擎（引擎代码未改）。
- **大盘词云里的词也写进下钻表**：大盘表 `wordcloud_map` 里出现的（词 + 情感）对应的下钻行保留，看板上点词云能下钻到评论。
- 运行日志写明用了哪些词、因关键字 / 因词云各保留多少行、去掉多少行。

> 取舍：加上词云规则后，过滤掉的行会少很多（样例数据 357 行只去掉 1 行）。
> 限制：近 90 日这类长周期词云可能用到早先日期的评论，那些日期的下钻行是当时按当时的词云过滤的；点词云下钻不到时，重算相应日期即可。

### 5. 性能：查询走索引 + 分段计时（`2fcf751`）

- **下钻过滤回查评论内容改为走索引**：原来每 1000 条评论做一次全表扫描，评论表越大越慢；现在按「渠道 + 景区 + 评论 ID」查，用上已有索引 `idx_comments_label_key`，这一步降到 0.0 秒。
- **运行日志按景区分段计时**，例如：
  `✓ 产出 3030 行（7.2s：计算 6.1s、下钻过滤 0.0s、写库 0.2s、推送 0.2s）`
- 为了单独量出写库时间，写库改由 smc 在计算完后调用引擎自带的 `load_all` 完成；规则不变（按景区 + 日期先删后写、一个事务）。

**实测**（20 万条评论、2 个景区、目标日期 + 往前重跑 3 天、开下钻过滤）：

| | 用时 |
|---|---|
| 单独跑引擎 | 15.6 秒 |
| smc 里跑 | 15.8 秒 |

时间几乎都在引擎计算本身，两边相同。

### 6. 演示数据（对应引擎的 `mock` 命令）

在「指标计算 → 计算」页新增「演示数据」，等同于：

```bash
python -m engin_cli.cli mock --from-scenic PFTSCA01016184 --to-scenic PFTSCA01018088 \
    --to-name 泰宁九龙潭生态旅游区 --start-date 20260928 --end-date 20261028 \
    --tables core,platform,dimension,content,drill,macro
```

- 填：从哪个景区复制、复制给的景区编号和名称、日期区间、推哪几张表；可勾「只组报文不发送」先验证。
- 复制逻辑用引擎自己的 `build_mock`：景区编号 / 名称换成新的；下钻表 `detail_uk` 按新景区重算，不会和原景区撞；`etl_time` 记成现在。
- **只推送，不写本地库。**推送按「推送」「推送表」里的地址、鉴权、表名、主键、字段；推哪几张表以这次勾选的为准（不看推送开关和「按景区推送」）。
- 保护：目标编号不能和源景区相同；目标景区在本系统里已有评论或指标数据时，确认框标红并写明会按主键覆盖下游里它的真实数据。
- 每次执行记一条运行记录，触发方式标「演示」，结果写明「源 → 目标：N 行，已推送 / 只组报文未发送」。
- 和计算共用一个运行位：有计算在跑时不能同时推演示数据。

## 三、已确认的行为

- **回刷天数全部写表**：每次计算的日期 = 目标日期 + 往前重跑 N 天（默认 3）。实测 6 张表写库和推送都覆盖了这 N+1 天；同样的日期重跑，行数不变（覆盖，不重复）。
- **微博 `work_url`**：`https://weibo.com/detail/{mid}` 里的数字就是 mid。

   - smc 里「计算的景区」是否为空（空 = 有评论的景区全部算）；
