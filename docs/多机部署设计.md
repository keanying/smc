# 多机部署：该怎么拆，以及为什么

写给"采集量会越来越大、在想要不要加机器"的时候看。

---

## 一、先说最反直觉的一条：加机器解决不了你的主要瓶颈

浏览器型采集（抖音 / 快手 / 小红书 / 微博）的上限**不是 CPU，是账号**。
一个账号每天能安全地搜多少次、打开多少条作品，是平台定的。

> 两台机器用同一个账号，不是采得快一倍，是**被封快一倍**。

所以"加一台机器"这个动作，只有在**同时加账号、并且账号和机器一一绑定**时
才真的提升产能。否则它只是把同一批账号的行为频率翻倍——正好是风控在看的信号。

反过来，HTTP 型采集（携程 / 同程 / 去哪儿档案）没有账号，瓶颈是**代理 IP 额度**，
这个是可以水平扩展的，而且代理池已经是 Redis 共享的（见第三节，全项目唯一
按分布式写对的模块）。

**结论：扩展轴是「按渠道类型拆」，不是「对称扩容」。**

---

## 二、你自己提的那个方案是对的

> "或一台机器来做浏览器采集？"

对。这是这套系统最合身的拆法：

```
                  MySQL（唯一事实来源）
                  Redis（去重/水印/代理池/标注队列）
                          │
        ┌─────────────────┼─────────────────┐
        │                 │                 │
  ┌─────▼──────┐   ┌──────▼──────┐   ┌──────▼──────┐
  │  主节点     │   │ HTTP 节点 1 │   │ HTTP 节点 2 │
  │ Web + 调度  │   │ 携程/同程/  │   │  （可随便加）│
  │ 浏览器采集  │   │ 去哪儿档案  │   │              │
  │ 账号 + 登录 │   │ 无账号无浏览器│  │              │
  │ profile 目录│   │             │   │              │
  └────────────┘   └─────────────┘   └─────────────┘
    ↑ 只有一台                          ↑ 这一层才是能扩的
```

**为什么这样拆，四个麻烦全部消失：**

| 麻烦 | 为什么消失 |
|---|---|
| profile 目录不能共享 | 只有一台机器有 profile，不存在共享问题 |
| 账号轮换撞车 | 只有一台机器在挑账号 |
| 浏览器内存闸门 | 本来就该按本机内存算，天然正确 |
| 登录窗口在哪台机器 | 只有一台能登录，不用路由 |

而能扩的那一层（HTTP 采集）恰好是**无状态**的：不碰账号、不开浏览器、
去重走 Redis SETNX、代理走 Redis 锁——这些已经写对了。

## 三、现在的代码在多机下具体哪里会坏

彻查过一遍，按严重度排。**这不是"可能有问题"，是确定会发生的。**

### 🔴 一上线就炸：任意一台机器启动，会杀掉另一台正在跑的任务

`task_repo.py:294` `reset_stuck_running()`：

```sql
UPDATE src_opinion_crawl_task SET status='failed', error='服务重启，任务被中断'
WHERE status IN ('running','queued')
```

**没有任何实例过滤。** 第二台机器一启动，或者你滚动发布重启任何一台，
就把另一台正在跑的任务全标成失败——任务其实还在跑、还在写数据，
但页面显示失败，而且槽位被释放，下一轮轮询会**再领一次**。

### 🔴 同一条任务被跑两遍

`scheduler.py:127` 每 5 秒轮询 DB 取任务，取任务的 SQL 是裸 SELECT
（`task_repo.py:191/202`），占位是一条**无条件** UPDATE（`scheduler.py:213`）：

```python
await self.tasks.update(task_id, {"status": "queued"})   # 没有 WHERE status='pending'
```

两个实例都会 UPDATE 成功，都会启动。定时任务到点时两台机器的轮询
几乎必然落在同一秒——重复不是偶发，是高频。

> `scheduler.py` 自己的注释写着"多副本部署时也只需给取任务加一把锁就能扩展"——
> 这把锁至今没写。现有的 `self._poll_lock` 是 asyncio 进程内锁。

### 🔴 账号轮换失效——而且是确定性撞车，不是竞态

`account_repo.py:135`：

```sql
SELECT * FROM src_opinion_social_account
WHERE channel=? AND enabled=1 AND status='active'
ORDER BY last_check_time ASC, id ASC LIMIT 1
```

没有 `FOR UPDATE`、没有 claim 列、挑中之后不写回任何东西。
两台机器跑同一条 SQL、同一个确定性排序、同一份共享数据 →
**必然返回同一行**。所有机器一起压同一个账号，正好是轮换机制想避免的。

单机上这一条被浏览器占用表（`slots.py`）挡住了，而那张表是**进程内 dict**——
多机下拦不住。

### 🔴 定时 Cookie 刷新会把好账号标成 expired

`scheduler.py:70` 的定时体检遍历共享 DB 里**全部**账号，逐个开 Chromium 取 Cookie。
B 机器上没有 A 机器的 profile → 取不到 → `mark_expired()` 写**共享 DB** →
A 机器上本来好用的账号被判死，下一条任务直接 LoginRequired。

而且它的"跳过忙碌账号"保护查的是**本机**占用表，所以 A 正在用的账号，
B 认为空闲，直接开——两台机器同时用同一个账号打同一个平台。

这条会**周期性自动发生**，不需要你做任何事。

### 🟡 补标会重复花钱

`labeling/manager.py:431` 的防重入只看本机的 `_jobs` dict，捞未标注行的 SQL
没有 claim。两台机器各起一个补标 → 都从 `LIMIT` 头部捞到同一批 200 行 →
双倍模型调用。作者在 L459 的注释里完整描述过这个失效模式，
他的解法"每批之间等队列排干"只能等本机的队列。

### 🟡 Redis 退化是静默的

Redis 连不上时会退化成**进程内 dict**（`redis_client.py:139`），服务照常启动。
此时去重、水印、代理锁全部变成本机的——同一条作品被 N 台机器各采一遍。

而 `MemoryStore.ping()` **恒返回 True**，监控看不出来。
多机部署必须把 `/api/health` 的 `redis_is_real` 接告警（v11.1 起有这个字段）。

### 🟡 取消按钮、看门狗、并发上限都只对一台机器生效

`_running` / `_cancel_events` / `_started_at` 都是进程内 dict（`scheduler.py:43`）。

- 任务跑在 B 上、请求打到 A：A 查不到 event，直接改 DB 状态并返回失败，**B 照常跑到底**
- B 上卡死的任务，A 的看门狗永远不会杀
- `max_running_tasks`（你设的 8）是**每实例**的，N 台 = 8N 并发

### 🟡 登录 / 直播窗口需要粘性会话

`live_session.py:577` 的会话表是进程内全局 dict。用户扫码的窗口在 A，
下一个请求打到 B 就 404。

### ✅ 这几样是对的，不用动

| 模块 | 为什么对 |
|---|---|
| 代理 IP 池 | Redis SETNX 分布式锁 + 双检（`proxy/pool.py:161`） |
| 作品级去重 | Redis SETNX 原子占位（`dedup_marks.py:129`） |
| 数据落库 | MySQL `ON DUPLICATE KEY UPDATE`，不会重复入库 |
| 浏览器内存闸门 | 进程内信号量，本来就该按本机内存算 |

注意最后一条的含义：**重复的是采集动作**（时间、流量、风控额度、标注费用），
数据本身不会重复入库。所以这类 bug 不会污染数据，但会烧钱和招风控。

## 四、要动手的话，按这个顺序

### 第 0 步：先确认你真的需要多机

在单机 v12（浏览器闸门）之后，先看一周的实际瓶颈：

- **顶栏「浏览器 N/M」长期顶满、任务在排队** → 需要更多账号 + 更多浏览器机器
- **CPU / 内存没顶、但采集就是慢** → 瓶颈在平台限流或代理，加机器没用
- **MySQL 慢查询多、数据中心页面卡** → 是数据库的问题，加采集机器无济于事

**别因为"数据会越来越多"就加机器**——数据多是 MySQL 的问题（分表、归档、
索引），和采集并发是两回事。

### 第 1 步：引入节点身份（最小改动，解决一半问题）

配置里加两项：

```yaml
server:
  node_id: "node-a"          # 每台机器唯一
  roles: ["web", "scheduler", "browser"]   # 这台机器干什么
```

然后：

1. **只有 `scheduler` 角色启动轮询和定时任务**——这一条最便宜，
   直接解决"任务跑两遍"和"Cookie 定时刷新互相干扰"
2. **`reset_stuck_running` 加 `WHERE node_id = ?`**——只清理自己的残留
3. 任务表加 `node_id` 列，`_launch` 时写上

### 第 2 步：任务领取改成 CAS

即使只有一个调度器也值得加，是纵深防御：

```sql
UPDATE src_opinion_crawl_task SET status='queued', node_id=?
WHERE task_id=? AND status='pending'
```

看 `affected_rows`，为 0 说明被别人抢走了，跳过。

### 第 3 步：任务按渠道路由到节点

浏览器渠道（douyin/kuaishou/xhs/weibo）只投给有 `browser` 角色的节点；
HTTP 渠道（ctrip/tongcheng/qunar）投给任意 `worker` 节点。

最简单的实现：轮询取任务时按角色过滤 channel。

### 第 4 步：标注队列改 Redis

```yaml
labeling:
  queue_backend: redis     # 默认是 memory（进程内）
```

Redis 队列本身带 lease / visibility timeout，多消费者是**安全的**——
多实例就是多消费者，正是想要的。补标另外加一把 Redis 锁。

### 第 5 步：把 `redis_is_real` 接告警

见上面"Redis 退化是静默的"。这一条不做，前面全白做。

## 五、如果只想最快跑起来（不改代码的过渡方案）

**两台机器，垂直分工，第二台关掉调度器**：

- 机器 A：完整服务（Web + 调度 + 浏览器采集 + 账号 + 标注）
- 机器 B：只跑 HTTP 渠道的档案采集，**`scheduler.enabled: false`**，
  由人工在页面上触发（档案采集本来就是手动触发的后台作业）

这样绕开了任务领取、定时刷新、账号轮换三个大坑，代价是机器 B 只能做档案，
不能跑定时采集任务。

⚠️ 即便这样，`reset_stuck_running` 那条还是会咬人——机器 B 启动时仍然会把
机器 A 的在跑任务标成 failed。**这一条必须先改**，改动只有一行 WHERE。
