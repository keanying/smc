## 1. 产品概述

产品名：**CloudSense 云听**（景区社媒舆情采集系统）。

**一句话**：按**景区**维度，把抖音、快手、小红书、微博、携程、同程、去哪儿上关于这个景区的
作品与评论采回来，统一入库，再用大模型给每条评论打上情感、维度、实体、关键词标签，供舆情分析和大屏使用。

| | |
|---|---|
| 目标用户 | 景区运营 / 文旅局舆情岗、为景区提供舆情服务的数据团队 |
| 解决的问题 | 七个平台各自翻、各自导，口径不一；评论量大，人工打标签跟不上 |
| 核心价值 | 一个景区一份配置，七个平台统一采集、统一口径入库；评论自动标注，人只做复核 |
| 交付形态 | Web 系统（前后端同端口），Docker Compose 一键部署，或裸机脚本启动 |

### 核心能力一览

- **多平台采集**：社媒四家（抖音 / 快手 / 小红书 / 微博）+ OTA 三家（携程 / 同程 / 去哪儿）
- **四种采集对象**：关键字搜索、指定用户主页、景区点评、指定作品链接
- **四种调度**：立即执行 / 指定时刻 / 固定间隔 / cron
- **账号体系**：多账号分组轮换、每日配额与冷却、冷却期间任务自动排队
- **AI 标注**：边采边标 + 一键补标历史 + 人工复核闭环
- **景区档案**：OTA 平台景区资料库，建景区时直接从库里挑
- **指标计算**（可选模块）：按景区算舆情指标六张表，定时计算、按表按字段推送给下游
- **集群部署**：多台机器共用一个库，主机派任务、从机跑任务；账号按机器归属，任务派到有号的机器（单机时既是主也是从）
- **运维友好**：实时日志、试搜、全平台体检、飞书告警、服务重启后自动续跑

## 2. 支持的平台

| 平台 | 采集对象 | 层级 | 是否需要登录 | 服务端排序 / 时间筛选 |
|---|---|---|---|---|
| 抖音 | 关键字 / 用户主页 / 作品链接 | 作品 → 评论（两级） | 需要 | 综合·最新·最多点赞 / 一天·一周·半年 |
| 快手 | 关键字 / 用户主页 / 作品链接 | 作品 → 评论（两级） | 需要 | 接口不支持，落库前本地按时间过滤 |
| 小红书 | 关键字 / 用户主页 / 作品链接 | 作品 → 评论（两级） | 需要 | 综合·最新·点赞·评论·收藏 / 一天·一周·半年 |
| 微博 | 关键字 / 用户主页 | 作品 → 评论（两级） | 需要 | 综合·实时·热门 / 任意日期区间 |
| 携程 | 景区点评 | 点评（多级回复） | 不需要 | — |
| 同程 | 景区点评 | 点评 | 不需要 | — |
| 去哪儿 | 景区点评 | 点评 | 不需要 | — |

说明：

- **时间范围在所有平台都成立**：接口能筛的先在接口筛，落库前再统一按时间窗过滤一遍。
  选「最新发布」排序时，翻到早于时间窗的内容会提前收工，不浪费请求。
- **采集方式**（仅抖音 / 快手 / 小红书）：
  - `接口`：只走接口，最快
  - `混合`（默认）：先走接口，被风控或拿不到数据时自动切换到拟人
  - `拟人`：浏览器模拟真人点击、翻评论，最慢但最不容易被拦
- **OTA 景区主页**：携程 / 同程 / 去哪儿的采集目标可以手工指定景区主页链接，
  写入作品表 `work_url`；不指定时才按平台规则自动生成。

## 3. 系统架构

```
              ┌──────────────── Web 界面（Vue3 + Element Plus）────────────────┐
              │ 概览 景区管理 景区档案 任务 数据中心 标注审核 账号管理 系统设置   │
              └───────────────────────────────┬─────────────────────────────────┘
                                              │ REST + WebSocket（实时日志 / 浏览器推流）
┌─────────────────────────────────────────────▼─────────────────────────────────────────────┐
│ FastAPI 后端                                                                               │
│  调度器（按 next_run_time 轮询，含「等待账号恢复」队列）                                     │
│  任务执行器 ── 各平台采集器（接口 / 拟人）── 浏览器池（Playwright，账号 profile 持久化）     │
│        │                         │                                                         │
│        │                         └── 代理池（快代理，按平台或全局分配出口 IP）               │
│        └── 边采边标 ──► AI 标注引擎（队列 + 多线程 worker + 失败池）──► 大模型（火山方舟） │
└──────────────┬────────────────────────────────────────┬────────────────────────────────────┘
               │                                        │
          MySQL 8（业务数据）                     Redis（代理 IP 缓存、标注队列、
                                                  失败池、账号轮换锁）
```

多台机器时（见 8.2）每台都是上面这一套，连同一个 MySQL 和 Redis：

```
                  MySQL + Redis（所有机器共用）
                            │
       ┌────────────────────┼────────────────────┐
  ┌────▼──────────┐   ┌─────▼────────┐    ┌──────▼───────┐
  │ 主机（主 + 从） │   │ 从机 B        │    │ 从机 C        │
  │ 选主、派任务    │──►│ 跑任务        │    │ 跑任务        │
  │ 也跑任务       │   │ 本机账号 profile│    │ 本机账号 profile│
  └───────────────┘   └──────────────┘    └──────────────┘
     页面连哪台都行：登录、实时画面、实时日志自动转到账号 / 任务所在的机器
```

| 组件 | 作用 | 是否必需 |
|---|---|---|
| MySQL 8.0+ | 景区、任务、作品、评论、账号、设置等全部业务数据 | 必需 |
| Redis 6+ | 代理 IP 缓存、标注队列与失败池、轮换锁 | 建议（标注队列可降级为进程内，重启会丢）；多台机器时必需 |
| Chromium（Playwright） | 登录、静默刷新 Cookie、拟人采集 | 社媒平台必需 |
| 火山方舟大模型 | AI 标注 | 开启标注时必需 |
| 快代理 | 出口 IP 轮换 | 可选 |
| 飞书机器人 | 需要人介入时告警 | 可选 |

## 4. 功能模块

### 4.1 概览

景区数、作品与评论总量、最近任务，以及各平台接入情况和账号状态。

### 4.2 景区管理

景区是整个系统的组织维度，所有采集、统计、标注都按景区归属。

- **景区**：手工添加（景区 ID + 名称），或 CSV 批量导入
- **关键字**，分三类：
  | 类型 | 用途 | 规则 |
  |---|---|---|
  | 主关键字 | 拿去平台上搜 | 决定「搜到什么」 |
  | 附关键字 | 景区的别名、相关说法 | 标题/描述/标签命中**任意一个**即视为相关 |
  | 过滤关键字 | 明确不要的内容 | 命中即丢弃，一票否决 |

  内容过滤可选：关闭（搜到什么存什么）/ 只按搜索关键字（默认）/ 搜索关键字 + 附关键字。
- **平台采集目标**：携程填 POI ID，同程填 sid，去哪儿可从景区档案挑选，社媒平台填作者主页 ID；
  OTA 平台可另填**景区主页链接**。

### 4.3 景区档案

携程 / 同程 / 去哪儿的**景区资料库**（名称、等级、地址、开放时间等），采一次落库。
之后建景区、加采集目标直接在库里搜索挑选，不用每次请求平台。
档案是景区资料，不是点评，不参与标注。

### 4.4 任务管理

**新建任务**：选景区 → 选平台 → 从景区带入关键字 → 设采集数量与排序/时间范围 → 选调度方式。

| 设置项 | 说明 |
|---|---|
| 采集数量 | 社媒：每关键字作品数、每作品评论数、是否采评论；OTA：点评数、最多翻几页（0 = 翻到底） |
| 统一 / 按平台 | 可所有平台统一设，也可按平台分别设，平台设置优先 |
| 调度 | 立即 / 指定时刻 / 固定间隔 / cron（支持 5 段标准与 6 段 Quartz，带下次执行预览） |
| 当天去重 | 当天已采成功的作品，重跑时跳过其评论，节省时间 |

**任务列表**：开始、暂停、取消、定时开关、在线编辑。运行中的任务也能编辑，改动从下一轮生效。

**任务详情**：WebSocket 实时日志、采集量统计、各平台生效的上限。

**任务状态**：

| 状态 | 含义 |
|---|---|
| 待执行 / 排队中 / 运行中 | 正常流转 |
| **等待账号恢复** | 该平台账号都在冷却中，任务进入队列；冷却结束后按**先到先执行**自动开跑 |
| 已完成 / 失败 / 已取消 / 已暂停 | 结束态 |

### 4.5 数据中心

- 顶部统计 + 景区 × 平台明细，点击即筛选
- 作品卡片列表，展开后逐级查看评论；图片、视频可直接查看播放（经过防盗链代理）
- **命中关键字**：标题最右侧显示这条作品是因为哪些关键字收录的——主关键字（搜到它的搜索词，蓝色）、
  附关键字（标题/描述/标签里出现的，灰色）；多个关键字搜到同一条作品时全部列出
- **删除作品**：复核觉得不相关可以删除，作品和已采到的评论一起删；删过的会记下来，之后的采集不会再收录它。
  携程/同程/去哪儿那一条是景区点评的集合，不能整条删除
- 导出 CSV（流式输出，中/英文表头可选，Excel 直接打开不乱码）

### 4.6 标注审核

评论入库后由 AI 自动标注，人在这里复核。

**标注产出**（写回评论表）：

| 字段 | 内容 |
|---|---|
| 情感 | 正向 / 中性 / 负向，及情感分值 |
| 维度标签 | 按维度体系打标（游玩体验、服务质量、设施环境、餐饮购物、安全秩序、交通接驳等），每条最多 6 个，必须命中体系白名单 |
| 实体标签 | 评论提到的具体对象 |
| 关键词 | 评论关键词 |

与景区无关的评论、纯表情等无效内容，由规则直接判为中性，不调用模型。

**标注 / 复核状态**（`label_review_flag`）：

| 值 | 页面显示 | 谁写 |
|---|---|---|
| 0 | 未标注 | — |
| 4 | AI 标注成功 | 引擎 |
| 5 | AI 标注错误 | 引擎（模型失败，没有产出标签） |
| 6 | 低置信 | 引擎（置信度低于阈值，建议人工看） |
| 1 / 2 / 3 | 复核正确 / 复核错误 / 复核成功 | 人工 |

> 「是否已标注」只看评论有没有标签；`label_review_flag` 表达的是 AI / 人工的意见。

**三种标注入口**：

| 入口 | 场景 | 说明 |
|---|---|---|
| 边采边标 | 日常 | 系统设置里打开后，新采到的评论自动进标注队列 |
| 一键补标历史未标注 | 历史数据、标注失败的数据 | 把范围内**所有没有标签的评论**（含 AI 标注错误的）送去标注；每条一轮只送一次，仍失败的下次再试；可按景区/平台限定范围，可中途停止，进度刷新页面不丢 |
| AI 再标 | 单条 | 同步标注这一条，立即返回结果 |

**可靠性**：

- 启动标注时**先把队列里剩下的标完，再从数据库拉未标注的**
- 服务重启、修改标注配置后自动续标；被关机打断的补标有断点，重启后接着补
- 默认 4 路并发；模型输出被截断时自动加大输出预算重试
- 页面「自检」会真实调用一次模型，模型被下线、Key 错误等问题在自检里就能看到并给出修复提示

### 4.7 指标计算（可选模块）

用采集到的评论（含 AI 标注结果）计算舆情指标，引擎是 `backend/vendor/opinion_metric_engine`。
在「系统设置 → 指标计算」打开后，左侧菜单出现「指标计算」页。

**逻辑独立**：自己的配置、自己的定时、自己的运行记录；每次计算在**独立子进程**里跑，
算得再久、内存再高也不影响采集服务。采集挂了也不影响它（它读的是库里已有的数据）。

**产出六张表**（写入 ADS 库，默认就是采集库）：

| 简称 | 表 | 内容 |
|---|---|---|
| 核心指标 | `ads_trf_social_opinion_comment_core_di` | 评论数、好中差评、环比、得分 |
| 平台分布 | `ads_trf_social_opinion_comment_platform_di` | 各平台评论分布与排行 |
| 维度得分 | `ads_trf_social_opinion_comment_dimension_score_di` | 三级维度得分 |
| 关键词云 | `ads_trf_social_opinion_comment_content_di` | 关键词云、负面突增词 |
| 下钻明细 | `ads_trf_social_opinion_drill_analysis_di` | 词 → 评论 → 作品 |
| 大盘 KPI | `ads_trf_social_opinion_macro_gran_metric_di` | 各周期粒度 × 渠道的 KPI |

**页面上能维护的**：

| 分页 | 内容 |
|---|---|
| 计算 | 立即计算（日期区间、景区、本次不推送）；运行记录：状态、每个景区的产出与推送结果、演示数据推送结果、分段计时、完整日志，可停止。运行中的日志通过 WebSocket **实时推送**，一行一行出来，标题旁显示「实时」；集群里在别的机器上算的也能看 |
| 演示数据 | **随计算自动推送**：配置「源景区 → 目标景区编号 / 名称 / 推哪几张表」，每次计算里源景区推送成功后，把它这次的结果换成目标景区再推一遍（日期相同，含往前重跑；不写本地库；主景区推送失败或本次不推送时跳过并写明原因）；**手动推一次**：从本地 ADS 表取一段日期复制推送，可先只组报文；目标景区在本系统已有真实数据时会醒目提醒 |
| 景区与参数 | 一张「计算配置」：范围（要算的景区，不选 = 有评论的全部景区）→ 取数（回溯天数、往前重跑、缺数回补）→ 口径（得分权重、关键词保留个数）→ 产出（下钻表 / 大盘表开关）→ 存储（是否写库、ADS 库名）。每一项下面写明影响哪几张表，鼠标移上去右侧 ADS 表会高亮；右侧另有表状态与一键建表 |
| 定时 | 开关 + cron（每次算「昨天」，再顺带重跑之前几天——评论会晚到） |
| 推送 | 地址、鉴权（请求头名 + 前缀 + 令牌，默认 `xpftkey: pfk_…`、不带前缀；令牌不回显）、报文字段名（默认 tableName / pkId / data）、附加字段、每批行数、超时、重试、成功标志字段、只组报文不发送；**预览报文**：按配置组出一个真实请求（curl 格式，令牌打码），对着下游接口样例核对 |
| 推送表 | **按景区推送**：一张「景区 × 表」的勾选表，第一行是默认（未单独配置的景区按它推），单独添加的景区只推它那一行勾的表；每张表：默认推不推、下游表名、主键（默认对齐下游数据网关的 pkId）、**推哪些字段、改成什么名字**（字段说明取自建表注释，主键字段必须推送） |

下钻明细的「只收评论内容含关键字的」：只看**评论自己的内容**，不看帖子 / 笔记 / 作品的标题；
关键字 = 本景区**启用的**主关键字 + 附关键字（过滤关键字、停用的不算）。
另外，大盘 KPI 表 `wordcloud_map` 里的词（按词 + 情感）也会写进下钻表，看板上点词云能下钻到评论。

推送在**写库之后**：推送失败不影响计算结果，修好后重算那几天即可（计算是幂等的，按「景区 + 日期」先删后写）。

### 4.8 账号管理

社媒平台需要登录账号；携程、同程、去哪儿不需要。

| 功能 | 说明 |
|---|---|
| 登录 | 在页面里打开远程浏览器（实时画面推流，可直接点击输入）完成登录 |
| 打开浏览器 | 已登录的账号直接打开带登录态的浏览器，不再跳登录页 |
| 导入 Cookie | 支持 Cookie-Editor 导出的 JSON 和请求头字符串，自动写入浏览器 profile |
| 静默保活 | 后台定时用账号 profile 刷新 Cookie，用户无感知；Cookie 失效能识别出来 |
| 试搜 | 用真实链路跑一个关键字，定位到底哪一步出问题 |
| 全平台体检 | 各平台挨个试搜一遍 |
| 账号分组 | 同组账号轮换采集 |
| 配额与轮换 | 按平台设置每日作品上限、单次连续工作时长、触发后冷却时长、轮换锁时长 |

**配额与冷却**：账号触发每日上限或连续工作时长后进入冷却。出厂建议值：

| 平台 | 每日作品 | 单次时长 | 冷却 |
|---|---|---|---|
| 小红书 | 150 | 45 分钟 | 180 分钟 |
| 抖音 | 300 | 90 分钟 | 120 分钟 |
| 快手 | 300 | 90 分钟 | 120 分钟 |
| 微博 | 500 | 120 分钟 | 60 分钟 |

所有值都可以在页面上按平台修改，填 0 表示不限制。

**轮换锁**：账号被派去采集后，锁定期内（默认 12 小时）排到候选名单最后，优先用没干过活的号；
只有一个号或所有号都在锁定期时仍会用它，不会让采集停摆。

### 4.9 集群

多台机器连同一个 MySQL 和 Redis 时，在这里看每台机器的状态。只有一台机器时它既是主也是从，页面上只有一行。

| 内容 | 说明 |
|---|---|
| 汇总 | 本机、当前主机、在线机器数、所有机器合计在跑的任务数 / 上限 |
| 机器列表 | 角色（主 + 从 / 主 / 从）、在线状态与心跳、在跑任务、浏览器占用与剩余内存、各平台账号（能用 / 总数）、访问地址、版本 |
| 接新任务 | 关掉后这台在跑的任务照常跑完，主机不再往这台派新任务；维护、重启机器前先关掉 |
| 删除 | 已下线的机器可以从列表删掉（它名下还有账号时要先迁走） |
| 点击跳转 | 机器名 → 派给这台的任务；「在跑 x / y」→ 这台正在跑的任务；账号格子 → 这台机器上这个平台的账号；访问地址 → 新标签页打开那台机器的页面；「运行中任务」卡片 → 所有在跑的任务 |
| 提醒 | 没有主机、调度被关、各台版本不一致、多台机器却没连 Redis、有账号还没分配机器 |

**主机与从机**：主机负责协调——把到点的任务派给合适的从机、把掉线机器上的任务标成中断、
跑指标计算的定时；从机负责运行采集任务。

**任务派给哪台**：一条任务整条派给一台机器。只派给在线、开着「接新任务」的机器；
任务指定了机器或点名了账号，就只派那台；否则挑有这个平台能用的号、又有空位的机器，
同样合适的挑最闲的。有号的机器都满了就等，不派给没号的机器。派给哪台、为什么还没派，都写进任务日志。

**账号归属**：账号在哪台机器上添加、扫码登录，就归那台（登录态存在那台的硬盘上），
采集只在那台用它。账号管理页多一列「机器」，添加账号时选机器；改机器 = 迁移，迁完要在新机器重新登录。

**页面打开哪台都行**：扫码登录、采集 Cookie、导入 Cookie、实时画面、任务实时日志、取消任务，
会自动转到账号 / 任务所在的机器上处理；系统设置在任意一台保存，所有机器几秒内同步。

### 4.10 用户管理与登录

登录本系统的人（不是社媒平台账号）。所有页面和接口都要先登录。

| 角色 | 能做什么 |
|---|---|
| 管理员 | 全部功能，含用户管理、系统设置、集群管理（接新任务开关、删除机器） |
| 操作员 | 日常操作：景区、任务、账号、复核、指标计算等；不能管用户、改系统设置、管集群 |
| 只读 | 只能看；可以改自己的密码 |

- **第一次使用**：还没有任何用户时，登录页变成「创建管理员」，建完直接登录。
- **用户管理**（管理员，在「系统设置 → 用户管理」）：添加用户（设初始密码和角色）、改角色、改显示名、停用 / 启用、重置密码、解锁、删除。
  停用、重置密码会让他所有地方的登录立刻失效；系统里至少保留一个启用的管理员。
- **右上角**：当前用户，可以修改密码、退出登录。改密码后其他设备上的登录都会退出。
- **安全**：密码 PBKDF2 加盐哈希；连续输错 5 次锁 10 分钟；会话 72 小时不用自动过期；Cookie 为 HttpOnly。
- **留痕**：评论复核人、任务创建人、指标计算的触发人记的是登录用户的显示名。
- **集群**：会话存在库里，在哪台登录都通用；机器之间互相调用用库里的内部令牌，不需要登录。
- **忘了管理员密码**：在服务器上运行 `python scripts/reset_password.py admin`。
- 不想要登录（只在本机自己用）：`config.yaml` 里 `auth.enabled: false`。

| 分页 | 内容 |
|---|---|
| 代理设置 | 快代理凭据、按平台/全局分配 IP、主动换 IP 频率，可在线测试 |
| 采集参数 | 默认采集数量、子评论层级、超时与重试、账号配额开关 |

## 5. 关键机制

| 机制 | 说明 |
|---|---|
| 采集容错 | 单条数据解析失败跳过；关键字级重试（默认 3 次）；一条作品的评论失败不影响整个平台；一个平台出错不影响其它平台 |
| 跨关键字去重 | 同一作品被多个关键字搜到只采一次评论 |
| 代理轮换 | 连接异常、超时、403/407/429/5xx 立即弃用当前 IP 并更换设备指纹；IP 缓存在 Redis，多进程不重复提取 |
| 冷却排队 | 账号全部冷却时，定时/手动任务转为「等待账号恢复」，恢复后按入队先后执行；浏览器被占用时 60 秒后重试 |
| 任务看门狗 | 卡死的任务会被识别并收尾 |
| 重启恢复 | 等待中的任务、标注队列、未补完的补标在服务重启后自动继续 |
| 防盗链图片代理 | 平台图片/视频经后端代理展示，且不会被滥用为通用代理 |

## 8. 部署与配置

### 8.1 部署

**Docker Compose（推荐）**

```bash
cp docker/.env.example docker/.env
cp config/config.example.yaml config/config.yaml
docker compose -f docker/docker-compose.yml up -d
```

- 前端：`http://<主机>/`
- 接口文档：`http://<主机>:8000/docs`
- 健康检查：`http://<主机>:8000/api/health`

**裸机**：Python 3.10+、MySQL 8.0+、Redis 6+；Linux/macOS 运行 `scripts/start.sh`，Windows 运行 `scripts\start.bat`。

**环境自检**

```bash
python scripts/selfcheck.py           # MySQL / Redis / 浏览器 / 代理 / 目标站点
python scripts/selfcheck.py --quick   # 只查 MySQL / Redis
```

### 8.2 集群部署

一台机器不用做任何配置（默认角色「主 + 从」）。加机器时：

1. 新机器部署同一版程序，`config.yaml` 的 `mysql`、`redis` 填和第一台**一样**的库
   （多台机器必须共用一个真实的 Redis：代理池、账号轮换锁、去重靠它共享）。
2. 每台机器写自己的集群配置（也可以用环境变量 `SMC_CLUSTER_ROLE=worker` 这样传）：

```yaml
cluster:
  role: worker              # all=主+从 / master=只协调 / worker=只跑任务
  node_id: worker-02        # 机器编号，集群里不能重复；留空=主机名
  node_name: 采集机 2        # 页面上显示的名字
  advertise_url: http://10.0.0.12:8000   # 主机能访问到这台的地址
  max_running_tasks: 0      # 本机最多同时跑几个任务；0=跟随系统设置
```

3. 启动后几秒内出现在「集群」页；在「账号管理」添加账号时选这台机器，扫码登录。

- 机器之间要能互相访问 `advertise_url`（主机转发登录、实时画面、日志要用）。
  Docker 部署时一定要显式填：容器里自动探测到的是容器内网 IP，别的机器访问不到。
- 几秒没心跳不算掉线，超过 `cluster.offline_seconds`（默认 30 秒）才算；掉线机器上的任务标成中断，周期任务照常排下一次。
- 可以有两台 `master` / `all`：同一时间只有一台是当前主机，它挂了另一台 30 秒内接手。
- 升级上来的老账号：第一台启动的从机把 profile 在本机硬盘上的认领过去；只有一台机器时全部归它。

设计取舍和每个多机问题的处理见 `docs/多机部署设计.md`。

### 8.3 配置优先级

```
代码默认值  <  config/config.yaml  <  环境变量 SMC_*  <  页面「系统设置」
```

- 页面能改：代理、采集参数、调度与浏览器、各平台参数、AI 标注、通知、指标计算（存在库里，所有机器共用）
- 只能改文件：MySQL、Redis、服务端口（避免在页面上把服务改挂）、集群配置 `cluster`（每台机器各自的）
- 环境变量：`SMC_<段>_<键>`，嵌套用双下划线，如 `SMC_PLATFORMS__CTRIP__MAX_PAGES=50`
- AI 标注的模型与 Key 以页面保存的为准；`config.yaml` 与标注引擎自带配置里的值作为初始默认

## 9. 常见问题

| 现象 | 处理 |
|---|---|
| 采集报「没有可用账号」 | 账号未登录、已失效或全部在冷却；看账号管理的状态和冷却时间，任务会自动排队等恢复 |
| 任务一直是「等待账号恢复」 | 正常排队；到账号管理检查冷却时长是否设得过大 |
| 第 1 页就没有结果 | 先用「试搜」定位：多为登录态失效或触发风控 |
| AI 标注全部失败 | 标注审核页点「自检」；常见原因是模型下线（ClosedEndpoint）或 Key 失效，在系统设置换模型后自动续标 |
| AI 标注错误的评论怎么重标 | 点「一键补标历史未标注」，没有标签的都会重新送标 |
| 登录窗口打不开 | 见 `README.md`「十二、排障」 |

## 10. 规划：景区端 + 企业端

> 设计阶段，尚未开发。

为了把系统部署进**景区本地盒子**，规划拆成两端：

| | 景区端（边缘盒子） | 企业端（云平台） |
|---|---|---|
| 部署 | 景区现场的盒子 | 我方云上 |
| 职责 | 本景区的采集、标注、复核 | 多景区汇总、计费、运营大屏 |
| 数据 | 本地存原始数据与加工指标 | 接收各景区同步的**原始数据 + 加工好的指标** |
| 登录 | 企业端统一 **SSO** | 账号、景区开通、权限 |
| 计费 | 上报大模型 **Token 用量** | 按 Token 计费 + 大屏服务费 |

界面设计稿已完成（景区端与企业端各页面）；后端的同步协议、SSO 与计费明细待排期。
